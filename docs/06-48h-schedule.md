# 48 小时代码优先执行排期

## 1. 总体门禁

- T+0：范围、数据版本和接口契约冻结；
- T+12：端到端最薄闭环可运行；
- T+24：全部基础项 P0 可验收；
- T+36：进阶项完成，功能冻结；
- T+42：公网和本地部署候选版冻结；
- T+48：提交物、演示与备用方案完成。

若资源不足，删除 P2，不得压缩安全测试、引用、部署复现和提交演练。

## 2. 分阶段任务

| 时间 | 交付目标 | 必做任务 | 退出条件 |
|---|---|---|---|
| 0–2h | [基线冻结](phases/phase-01-baseline-freeze.md) | 复核追踪矩阵；建立仓库、分支、env；确认部署账号和模型配额 | P0 owner 与验收标准明确 |
| 2–6h | [数据可用](phases/phase-02-knowledge-ingestion.md) | PDF 解析、页级校验、结构化事实、chunk、manifest、seed/migration | A/B/C 可按角色查询，关键表格人工复核 |
| 6–12h | 最薄闭环 | FastAPI chat；路由；检索；provider；引用；Next.js 聊天和流式状态 | 浏览器完成一次带页码引用的动态问答 |
| 12–18h | 推荐与安全 | 健康档案、规则候选、禁忌硬过滤、风险分级、输出校验 | 三类方案、多类禁忌和拒答 API 测试通过 |
| 18–24h | P0 完整 | 多轮记忆、会话 CRUD、错误态、响应式、Compose、基础文档 | 追踪矩阵全部 P0 有代码与测试证据 |

| 36–42h | 稳定与部署 | 全回归、性能、限流、密钥扫描、公网 HTTPS、干净环境复现 | release candidate、URL、Compose 全通过 |

| 46–48h | 最终提交 | 匿名克隆、链接、权限、截止时间、hash/tag、提交回执 | 双人或双清单复核完成 |

## 3. 角色分工

四人推荐：

- A：后端/RAG/模型适配；
- B：前端/交互/响应式；
- C：知识整理/安全/评测；
- D：DevOps/测试/文档/演示统筹。

两人推荐：一人负责 API、RAG、数据与部署；一人负责 Web、评测、文档与演示，安全规则共同复核。

单人模式：严格串行走 0–24h 主链路，账号系统、评测页和下载摘要按顺序降级。每 3 小时打一个可运行 tag，不同时重构前后端。

## 4. 每个阶段的工作纪律

- 每项开发先写对应需求 ID 和验收断言；完成后马上补测试和证据路径。
- 数据、Prompt、代码和部署配置均进版本控制，真实 Secret 除外。
- 主分支始终可部署；高风险改动使用短分支，避免临近提交大合并。
- 每 6 小时运行一次黄金集；T+30 后每次合并都运行 P0 门禁。
- T+36 后只修 P0/P1 缺陷，不增加依赖、不换数据库、不换 UI 框架。

## 5. 降级顺序

时间或 API 配额出现问题时，按以下顺序缩减：下载摘要 → 评测可视化 → 历史搜索 → 注册账号 → P1 视觉动效。匿名会话、动态模型、A/B/C 隔离、引用、安全门、推荐、多轮、响应式、公网/Compose、文档和测试不得删除。

模型故障时允许切换兼容 provider；若主模型不可用，界面明确提示并保留食材/方案的确定性查询能力。数据库向量扩展不可用时，小语料降级为精确关键词和字符相似度检索，但不降级来源过滤和引用校验。

## 6. 每日站会格式

每次只记录四项：已通过的需求 ID、阻塞及影响、下一时段 P0、需要冻结的决策。所有“完成”必须指向测试或截图；没有证据只算开发中。
