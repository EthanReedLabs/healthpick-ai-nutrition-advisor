# AI 智能膳食顾问主执行方案

## 1. 执行结论

本赛题应按“可审计的健康领域 RAG 产品”实施，而不是普通聊天机器人。取胜关键不是堆叠最多功能，而是同时做到以下四点：

1. 基础需求零缺失，避免总分被封顶在 59 分；
2. A/B 与 C 在检索层硬隔离，引用和数值可以逐条核验；
3. 推荐、安全、多轮和异常处理有确定性规则，不把全部判断交给 LLM；
4. 用自动测试、评测报告、部署地址和演示脚本证明工程完成度。

赛题原文缺少若干详细评分条款。本方案采用对参赛者更严格的默认解释：只有标题没有细则的项目，也必须实现并留下证据。

## 2. 产品定位

产品名建议：`HealthPick 智膳顾问`。

一句话价值：根据用户目标、基础身体信息和饮食禁忌，从官方资料中提供有出处、能解释、不过度医疗化的营养问答与饮食方案建议。

目标人群：

- 减脂塑形：需要热量范围、三餐搭配、低 GI 和食材替换；
- 增肌强化：需要蛋白质目标、训练日前后饮食和增肌方案；
- 稳糖调理：需要低 GI、控糖餐盘、进食顺序和风险提示；
- 平台访客：询问会员、企业服务、API、渠道合作等平台信息。

产品明确不是医疗诊断工具。确诊疾病、孕哺期、术后等高风险情况只能提供资料范围内的一般信息并引导专业人员。

## 3. 冲分策略

### 3.1 P0：基础项，24 小时内全部打通

- A/B/C 原始资料入库、版本和哈希记录；
- 营养与平台意图路由；
- A/B 与 C 检索硬隔离；
- 动态 LLM 回答与流式输出；
- 文档名、章节、页码和原文片段引用；
- 减脂、增肌、稳糖方案匹配；
- 过敏、糖尿病/血糖、高尿酸、肾病、麸质、孕哺期安全门；
- 多轮记忆、会话创建/切换/删除；
- 空输入、超长输入、特殊字符、无关问题和服务异常处理；
- 响应式 Web 最小闭环；
- 至少 20 条自动化测试和一键运行。

P0 未通过时禁止投入高级视觉效果、复杂图表或额外第三方集成。

### 3.2 P1：主要加分项，36 小时内完成

- 用户注册/登录，匿名会话可迁移到账号；
- 历史对话持久化、搜索、重命名、删除；
- 健康档案和禁忌信息持久化；
- 方案卡片、7 日计划、食材替换和购物清单展示；
- 食材营养结构化查询与对比；
- 模型来源、知识版本和生成时间透明展示；
- 公网 HTTPS 部署；
- Docker Compose 本地一键启动；
- 50 条以上黄金/对抗评测和机器可读报告；
- 管理/评测页展示通过率、延迟和失败用例。

### 3.3 P2：差异化亮点，42 小时前按风险选做

- 回答中的引用高亮与“为什么推荐”证据抽屉；
- 当前会话画像变化时间线；
- 方案食材自动替换预览；
- 可访问性检查、键盘操作和减少动态效果模式；
- 演示模式：预置经过验证的用户画像和问题，不硬编码回答；
- 生成可下载的个人方案摘要，但必须复用已经验证的内容与引用。

不建议在 48 小时内做食物拍照识别、智能设备接入、复杂知识图谱和支付。这些来自素材 C 的产品愿景，不是赛题验收项，投入产出比低。

## 4. 核心用户流程

### 4.1 首次访问

1. 显示产品能力、AI/医疗边界和三个快捷入口；
2. 用户选择减脂、增肌、稳糖或“先问问题”；
3. 仅收集当前回答必要的数据：年龄范围、性别、身高、体重、活动水平、目标、过敏和特殊情况；
4. 计算 BMI 时注明“系统估算”，展示公式和输入值；
5. 如发现高风险情况，先展示安全提示，再进入受限问答模式。

### 4.2 营养问答

1. 请求进入输入校验和安全预检查；
2. 意图路由到 `nutrition_qa`；
3. 检索仅允许 A/B；
4. 证据不足则追问或明确说资料中没有答案；
5. LLM 只能根据证据生成；
6. 引用校验器检查数字、禁忌和结论；
7. UI 以答案、行动建议、风险提示、来源卡片四层展示。

### 4.3 方案推荐

1. 规则引擎根据目标和安全状态生成候选方案；
2. 高风险用户不生成个性化营养数字，只返回一般原则和就医建议；
3. 检索 B 获取方案定位、目标、食谱和替换规则，检索 A 补充营养依据；
4. 返回 1 个主方案，必要时加 1 个备选，而不是同时堆出三套方案；
5. 每个推荐给出“匹配原因、关键目标、可执行三步、替换建议、来源”；
6. 用户可在后续对话中提出偏好或过敏，系统保留上下文并重算候选。

### 4.4 平台问答

1. 价格、会员、企业服务、API、合作方式等路由到 `platform_qa`；
2. 只检索 C；
3. 回答使用平台资料中的价格、服务和联系方式；
4. C 中的信息不得写入健康画像，不得成为膳食方案推荐依据。

### 4.5 混合问题

例如“专业版多少钱，顺便给我一个减脂方案”。系统将问题拆成两个子任务：

- 平台子任务只查 C；
- 营养子任务只查 A/B；
- 最终答案分区展示，引用各自独立，禁止把 C 的销售内容注入营养部分。

## 5. 功能模块

### 5.1 Web

- 欢迎页与快捷目标卡；
- 流式聊天、停止生成、重试和复制；
- 来源卡片：文档、章节、页码、证据摘录；
- 健康档案抽屉；
- 方案页：方案摘要、营养目标、7 日计划、替换规则；
- 食材查询/对比；
- 历史记录列表与详情；
- AI 透明度页面：模型标识、知识版本、免责声明；
- 评测概览页：只展示脱敏后的测试结果。

### 5.2 API

- 输入限制、请求 ID、结构化日志、统一错误码；
- 鉴权、匿名会话和账号迁移；
- 健康档案 CRUD；
- 会话和消息持久化；
- 意图路由、检索、RRF、证据门、生成和引用校验；
- 方案规则与禁忌规则；
- 知识导入、版本检查和重建；
- 评测运行与报告导出；
- `/health/live` 和 `/health/ready`。

### 5.3 建议 API 契约

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/chat/stream` | 流式问答，返回事件和最终引用 |
| GET | `/api/v1/conversations` | 历史会话列表 |
| POST | `/api/v1/conversations` | 创建会话 |
| PATCH | `/api/v1/conversations/{id}` | 重命名 |
| DELETE | `/api/v1/conversations/{id}` | 删除会话及消息 |
| GET/PUT | `/api/v1/profile` | 读取或更新健康档案 |
| POST | `/api/v1/recommendations` | 生成结构化方案推荐 |
| GET | `/api/v1/foods/search` | 查询人工校验的食材事实 |
| GET | `/api/v1/about/model` | 返回实际模型和知识版本 |
| POST | `/api/v1/evals/run` | 受保护的离线评测入口 |
| GET | `/health/live` | 进程存活 |
| GET | `/health/ready` | 数据库、知识和模型依赖就绪 |

聊天请求必须包含 `conversation_id`、`message`、`client_message_id`。服务端用 `client_message_id` 实现幂等，避免网络重试产生重复消息。

## 6. 数据模型

最小实体：

- `users`：账号和状态；
- `user_profiles`：目标、基础信息、饮食偏好、安全标记；
- `conversations`：所有者、标题、摘要、更新时间；
- `messages`：角色、原文、结构化答案、模型、延迟；
- `message_citations`：消息与证据 Chunk 的多对多关系；
- `documents`：A/B/C manifest、版本、哈希和角色；
- `knowledge_chunks`：章节文本、页码、标签、embedding；
- `food_facts`：人工校验的每 100 克食材数据；
- `plan_rules`：方案目标、适用条件、替换和安全标签；
- `retrieval_traces`：脱敏检索结果、分数和路由；
- `eval_runs` / `eval_cases`：评测输入、结果和证据。

健康档案字段应最小化。不要保存自由文本疾病详情；用经过定义的安全标签保存必要状态，并提供删除功能。

## 7. RAG 与推荐原则

详细设计见 [知识库与 RAG](03-rag-and-knowledge.md)。必须遵循：

1. 先路由和安全判断，再检索；
2. `source_role` 是数据库过滤条件，不只是 Prompt 文案；
3. 小规模语料优先精确向量检索，避免近似索引损失召回；
4. 数字、GI、热量和宏量营养素优先查人工校验事实表；
5. 每条健康结论至少有一个直接支持证据；
6. 无证据时拒绝编造；
7. 生成后校验引用，失败只允许自动重试一次；
8. 保存检索 trace，方便评委追问时展示工程过程。

## 8. 医疗、安全和隐私

详细设计见 [医疗安全与隐私](04-safety-privacy.md)。关键策略：

- LLM 前置和后置两道安全门；
- 高风险标签由规则引擎判定，不由模型自由发挥；
- 不诊断、不调整药物、不承诺治疗效果；
- 确诊疾病、孕哺期、肾病等不输出个性化热量/蛋白质处方；
- 所有疾病相关回答追加赛题规定的免责声明；
- 资料中的指令视为数据，不执行 PDF 中可能存在的提示注入；
- 密钥、日志、用户健康信息分开管理；
- 支持导出和删除个人数据。

## 9. UI 验收标准

- 375px、768px、1440px 三档无横向溢出；
- 欢迎、输入、加载、成功、无证据、错误和重试状态完整；
- 输入为空时不发送，超长输入在前后端双重限制；
- 来源可点击展开，引用信息不挤入正文；
- 快捷操作至少包括“生成减脂方案”“训练后怎么吃”“稳糖怎么搭配”“平台会员有什么”；
- 颜色不是唯一状态提示；关键控件有可访问名称和键盘焦点；
- 移动端历史记录和档案使用抽屉，不压缩聊天区；
- 不以炫技动画影响首次响应和阅读。

## 10. 质量门

功能进入主分支前必须通过：

- Python lint/type/unit；
- TypeScript lint/type/unit；
- 数据库迁移可正向执行；
- API contract tests；
- P0 浏览器 E2E；
- RAG 黄金集；
- A/B/C 串库对抗集；
- 高风险安全集；
- `.env`/密钥扫描；
- Docker Compose smoke test。

建议竞赛目标：

- 路由准确率 ≥ 98%；
- 串库泄漏为 0；
- 高风险安全召回率 100%；
- 黄金集数字准确率 100%；
- 引用支持率 ≥ 95%；
- 空/长/特殊/无关输入 0 个未处理 5xx；
- 正常网络下首 token P95 ≤ 3 秒；
- Docker 冷启动后 15 分钟内可完成评委复现。

## 11. 部署方案

主环境：

- Web 部署到支持 Next.js Node runtime 的 HTTPS 平台；
- API 部署为 Docker 容器；
- PostgreSQL 使用支持 pgvector 的托管实例；
- Web/API/DB 分别配置健康检查、环境变量和日志；
- 演示 URL 至少保留 7 天。

兜底环境：

- `docker compose up --build` 启动 web、api、postgres；
- `scripts/seed` 导入资料、演示账号和验证用例；
- README 提供 Windows 与 macOS/Linux 命令；
- 没有外部模型密钥时显示明确配置错误，不伪造回答。

## 12. 提交物

- 可访问演示 URL 和有效期说明；
- Git 仓库；
- Docker Compose 和一键脚本；
- 使用说明，正文不少于 500 字；
- 技术选型与核心逻辑不少于 200 字；
- 系统架构说明不少于 300 字；
- 至少 5 组测试记录，实际目标 50+；
- 架构图、RAG 流程图和数据库图；
- 评测报告、测试截图和演示视频；
- AI 辅助模块与人工优化说明；
- `.env.example`，无真实 API Key。

## 13. 风险登记

| 风险 | 触发信号 | 预防/降级 |
|---|---|---|
| PDF 表格抽取错误 | 数值错列、单位丢失 | 数值事实人工复核，golden test 锁定 |
| A/B/C 串库 | 营养回答出现价格或销售话术 | 数据库硬过滤 + 对抗集 |
| LLM 编造 | 无证据仍给数字 | 证据门 + 数字事实表 + 引用校验 |
| 医疗越界 | 确诊疾病仍生成处方 | 前置规则阻断 + 后置扫描 |
| 模型 API 不稳定 | 超时、限流、区域不可用 | Provider adapter、重试、熔断、备用模型 |
| 公网部署失败 | 构建或健康检查失败 | Docker Compose 兜底，T34 前部署 |
| 用户系统拖延 | 认证问题占用 P0 时间 | 匿名会话先行，账号功能 P1 |
| 功能过载 | T36 后仍新增需求 | 功能冻结，仅修缺陷和证据 |
| 演示不可复现 | 账号、URL、数据失效 | 演示账号、seed、录屏、双运行路径 |

## 14. 明确不做

- 不把 C 的价格、会员权益或成功案例用于膳食推荐；
- 不使用硬编码答案通过演示；
- 不对 PDF OCR 结果未经复核就写入营养事实表；
- 不在仓库提交真实密钥、真实健康数据或生产日志；
- 不承诺减重、逆转疾病或治疗效果；
- 不在 T36 后更换核心框架、数据库或模型协议；
- 不为了“看起来高级”引入知识图谱、微服务或复杂 Agent 群。

## 15. 开工顺序

1. 将本方案和需求矩阵设为范围基线；
2. 创建数据库迁移、共享 schema 和健康/错误接口；
3. 完成 A/B/C 生产级提取、结构化复核和 seed；
4. 完成隔离检索、引用和安全门的 API 测试；
5. 接入动态 LLM 和流式聊天；
6. 完成 P0 Web 流程；
7. 再开发用户、历史、评测页和公网部署；
8. 按 [48 小时排期](06-48h-schedule.md) 冻结、验收和提交。
