# 评测体系与冲分策略

## 1. 核心思路

高分不靠功能数量堆叠，而靠“每个赛题要求都有功能、测试和可展示证据”。评测同时覆盖答案质量、知识隔离、安全、工程稳定性、用户体验和可复现部署。所有演示亮点必须建立在 P0 全绿之上。

## 2. 黄金评测集

首个可提交版本目标 72 条固定用例：

| 集合 | 数量 | 验证内容 |
|---|---:|---|
| A 基础营养事实 | 14 | 营养素、餐盘、食材、禁忌、页码引用 |
| B 方案与替换 | 14 | 减脂、增肌、稳糖、替换规则和方案边界 |
| C 平台事实 | 8 | 套餐、平台能力、企业合作，仅引用 C |
| 路由与混合问题 | 10 | A/B/C 分类、混合拆分、0 串库 |
| 多轮记忆 | 8 | 目标、忌口、偏好、方案修改与会话隔离 |
| 医疗安全 | 10 | S1/S2/S3 触发、禁忌排除和专业提示 |
| 对抗与鲁棒性 | 8 | 注入、无答案、超长、特殊字符、模型异常 |
| 合计 | 72 | 可持续扩充，不以随机抽样替代固定回归集 |

每条用例保存：`id`、用户画像、对话轮次、期望路由、允许来源、禁止来源、事实断言、引用断言、安全断言、拒答条件和评分权重。数字类、禁忌类和方案边界由人工从原 PDF 双人复核后录入。

## 3. 指标和发布阈值

| 指标 | 计算方式 | P0 阈值 | 冲分目标 |
|---|---|---:|---:|
| 路由准确率 | 正确 route / 全部 route 用例 | ≥95% | ≥98% |
| 来源泄漏率 | 出现禁止 source_role 的回答 / 全部回答 | 0 | 0 |
| 数字事实准确率 | 精确匹配的数字断言 / 数字断言总数 | 100% | 100% |
| 引用支持率 | 被引用证据直接支持的主张 / 可核验主张 | ≥90% | ≥95% |
| 高风险召回率 | 正确识别 S2/S3 / S2/S3 总数 | 100% | 100% |
| 禁忌冲突率 | 推荐中包含 blocked tag / 有禁忌推荐 | 0 | 0 |
| 多轮约束保持率 | 后续仍满足画像约束 / 多轮断言 | ≥95% | 100% |
| API 稳定性 | 自动用例中的未处理 5xx | 0 | 0 |
| 首字响应 P95 | 用户提交到首个流式 token | ≤5 秒 | ≤3 秒 |
| 公网可用性 | 演示期健康检查成功率 | ≥99% | ≥99.5% |

LLM 评审只能作为补充分数，不作为安全、数字和来源隔离的唯一判据。确定性断言优先使用代码校验。

## 4. 测试分层

1. 单元测试：路由、风险规则、候选过滤、RRF、引用校验、Schema 校验。
2. 数据测试：manifest/hash、页码范围、结构化事实唯一性、A/B/C 角色约束。
3. API 集成：对话、检索、用户、历史、删除、导出、限流、模型降级。
4. RAG 离线评测：72 条黄金集，固定知识版本和 provider 配置，生成 JSON/Markdown 报告。
5. 浏览器 E2E：375、768、1440 三种视口；主流程、错误态、键盘操作和引用展开。
6. 部署验收：全新环境 Docker Compose 启动、公网 smoke、数据库迁移、备份恢复。

## 5. 评委可见证据包

`evals/reports/<release-id>/` 固化以下内容：

- `summary.json`：版本、commit、知识哈希、模型、指标；
- `golden-results.jsonl`：每条期望与实际；
- `safety-report.md`、`source-isolation-report.md`；
- `api-test.xml`、`e2e-report/` 和三档视口截图；
- `latency.csv` 与失败用例清单；
- 演示环境健康检查结果。

透明页只展示已经生成并入库的报告，不实时伪造百分比。现场可点开一个回答的 route、检索片段、来源页码和校验状态，以证明系统是动态 RAG 而非硬编码回复。

## 6. 冲分功能排序

| 顺序 | 功能 | 理由 | 停止条件 |
|---:|---|---|---|
| 1 | 准确引用 + A/B/C 隔离 | 直接命中赛题核心，降低重大失分 | 串库 0、引用目标达标 |
| 2 | 个性化计划 + 多轮约束 | 展示智能和可用性 | 5 组多轮 E2E 全通过 |
| 3 | 安全门 + 禁忌过滤 | 健康场景底线，也是专业度亮点 | 安全集全绿 |
| 4 | 响应式产品界面 | 提升第一印象和完成度 | 三档视口全绿 |
| 5 | 用户、历史和数据权利 | 明确进阶能力 | 权限/删除 E2E 通过 |
| 6 | 透明评测页 | 让工程能力可见 | 只读报告稳定展示 |
| 7 | 下载方案摘要 | 产品化加分 | 不影响核心链路 |

不开发食物图片识别、智能硬件接入、支付、复杂知识图谱或自动网络营养搜索。这些功能会稀释 48 小时内对核心评分项的完成质量。

## 7. 失败处理

每次回归先列出失败的需求 ID。P0 失败立即停止 P1/P2；不以重跑掩盖不稳定用例。模型非确定性用例允许有限重试，但报告必须同时记录首轮结果和最终结果。发布前使用新匿名用户从公网完整演练一次，避免只在开发者本机会成功。
